## Domain

This system aggregates student-generated course and professor reviews to provide transparency around grading curves, teaching styles, and actual weekly workloads. This knowledge is highly valuable for students managing strict GPA or major tracking requirements, yet it remains impossible to find through official university channels, which only offer sterile, summarized syllabus descriptions. By capturing crowd sourced student experiences, the guide bridges the gap between official course listings and the lived reality of the classroom.

## Chunking Strategy

<!-- Describe your chunking approach with enough specificity that someone else could reproduce it.
     Include:
     - Chunk size (characters or tokens) and why that size fits your documents
     - Overlap size and why (or why not) you used overlap
     - Any preprocessing you did before chunking (e.g., stripping HTML, removing headers)
     - What your final chunk count was across all documents -->

**Chunk size:**
800 characters (approx. 150-200 tokens)
**Overlap:**
150 characters (approx. 30-40 tokens)
**Reasoning:**
My corpus is a mix of sprawling, multi-paragraph Reddit narratives and rapid-fire Discord/Rate My Professor reviews. A medium chunk size of 800 characters is large enough to capture the full context of a detailed Reddit comment (ensuring a professor's name stays connected to their specific grading policies mentioned a few sentences later), while small enough to prevent blending multiple unrelated short RMP reviews together. The generous 150-character overlap prevents critical modifiers—such as "However, the final is heavily curved"—from being severed from the main complaint about a difficult midterm in the preceding sentences.
**Final chunk count:** 1 chunk (approx. 1,363 characters total; roughly 270 tokens)

## Embedding Model

<!-- Name the embedding model you used and explain your choice.
     Then answer: if you were deploying this system for real users and cost wasn't a constraint,
     what tradeoffs would you weigh in choosing a different model?
     Consider: context length limits, multilingual support, accuracy on domain-specific text,
     latency, and local vs. API-hosted. -->

**Model used:**
all-MiniLM-L6-v2 (via sentence-transformers)
- 384-dimensional embeddings
- Runs locally (no API key or rate limits)
- Fast inference (~1ms per chunk on CPU)
- Pre-trained on 100M sentence pairs; excellent for semantic search

**Top-k:**
5 (retrieve top 5 most relevant chunks per query)
- Rationale: Balances retrieval quality with context window efficiency; provides diverse perspectives without overloading the LLM. Will tune based on actual retrieval quality during evaluation.

**Production tradeoff reflection:**
For real-world deployment, I would consider:
1. **Context length vs. accuracy**: all-MiniLM-L6-v2 has a 128-token max input. For longer chunks or multi-paragraph reviews, a model like `all-mpnet-base-v2` (384 dims, 514 tokens) would preserve more context but add latency.
2. **Domain-specific fine-tuning**: If accuracy on course/professor reviews is critical, I could fine-tune a model on the domain. However, all-MiniLM generalizes well to reviews and opinions.
3. **Multilingual support**: If the corpus included non-English reviews, I'd use `multilingual-all-MiniLM-L12-v2`. For English-only, all-MiniLM-L6-v2 is optimal.
4. **Cost/latency tradeoff**: All-MiniLM runs on CPU and requires ~4 seconds to embed 1000 chunks; OpenAI's `text-embedding-3-small` would be faster for real-time queries but costs ~$0.02 per 1M tokens and requires API calls.
5. **Batch size optimization**: Could increase batch size for embedding to parallelize; already using batch `collection.add()` in ChromaDB.

## Grounded Generation

This system enforces grounding in two ways: a strong system prompt and a retrieval filter.

**System prompt grounding instruction:**

The model receives a system-level instruction that says, in effect:

- "Answer only using the information provided in the documents. Do not use any outside knowledge."
- "If the documents do not contain enough information to answer the question, respond exactly: \"I don't have enough information on that.\""
- "When you answer, include source citations in this exact format: [README.md, chunk 0]. Use the source document name from the 'Source' field in the context, not the context section label. Do not invent or hallucinate sources."

The user prompt then supplies a formatted context block with retrieved chunks explicitly labeled as:

- `Source: README.md`
- `Chunk: 0`
- `Text: ...`

This makes the source names visible and forces the model to ground its answer in the retrieved text.

**How source attribution is surfaced in the response:**

The response is expected to include explicit citations like `[README.md, chunk 0]` whenever it makes factual claims. In addition, the system appends a programmatic source summary after generation showing which retrieved documents were used, e.g. `Sources used: README.md`.

## Failure Case Analysis

**Question that failed:** What is the dining hall menu for lunch today?

**What the system returned:** I cannot find this information in the student reviews. Try asking about specific professors, courses, workloads, exam formats, grading policies, or lecture attendance requirements.

**Root cause (tied to a specific pipeline stage):** The failure occurred in the retrieval stage because the documents do not include dining hall menu information. The vector store returned only an unrelated `README.md` chunk with a high distance score, so the system correctly refused to answer rather than hallucinating.

**What you would change to fix it:** Add documents that actually cover dining hall or campus dining menu content, or restrict the user-facing domain more explicitly to course and professor reviews. Better corpus coverage is the fix here, not a model change.
